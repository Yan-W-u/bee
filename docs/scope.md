# bee 的适用范围（以及它不是什么）

这份文档存在的唯一目的：让你在花时间之前就知道边界在哪。
结论先给——**bee 不是 SAST 替代品，它的价值在「发现之后」**。

## 它擅长什么

| 能力 | 说明 |
| --- | --- |
| 把命中讲成人能 review 的论证 | 四段式：根因 / 攻击路径 / 影响面 / 修复原理，每条结论必须指回真实行号 |
| 生成补丁并**机器验证** | `applied` / `finding_gone` / `compiles` / `tests_pass` 四项信号，缺一不可 |
| 给 CI 一个可复现的门禁 | 规则档位 + baseline 指纹，只对新增问题负责，输出 SARIF 给 Code Scanning |
| 接收外部扫描结果 | `--input <sarif>` 可把 Semgrep / CodeQL 的结果接进来，只做解释与修复 |

## 它不擅长什么

**1. 覆盖率。** 内置 30 条规则覆盖的是最高频的模式化漏洞。业务逻辑漏洞
（越权、竞争条件、状态机绕过）它发现不了。需要覆盖率就接 Semgrep
（`--detector semgrep` / `--detector both`）或直接用 CodeQL，然后把结果用
`--input` 喂给 bee。**合规场景（等保、PCI-DSS）请上商业 SAST。**

**2. 跨过程数据流。** 内置检测是「单文件 + 轻量变量追踪」。跨函数、跨服务的
污点传播不在能力范围内——那是 CodeQL 的领域。

**3. 内置规则的真实精度不足以直接当门禁。** 见下节数字。

## 内置规则在真实代码上的表现

以 CPython 3.13 stdlib（536 个文件，排除 test / site-packages / idlelib）为语料，
`--detector rules --profile default`：

| 版本 | 发现数 | 说明 |
| --- | --- | --- |
| v1.0.0 | 321 | 其中大部分是误报：`iscoroutinefunction(` 被 JS 的 `Function(` 分支命中、docstring 里的示例代码、`token_type = '...'` 被当成硬编码凭据 |
| v1.1.0 | **81** | 加了词边界、按语言拆分 pattern、字符串/注释过滤、凭据启发式、timing 收紧 |

剩下的 81 条里仍然混着误报，主要来自「规则只看单行，看不到上下文」的固有局限，
例如 `eval(code, globals, locals)` 在调试器实现里是正常用法。
**这就是为什么默认档叫 default 而不是 strict，也是为什么报告必须人 review。**

分档建议：

- `--profile strict`：只报高把握规则。适合放进 CI 门禁，宁可漏报。
- `--profile default`：默认档。适合人看。
- `--profile full`：全量启发式。适合一次性摸底，噪音大。

## `finding_gone` 证明什么、不证明什么

它证明的只有一件事：**打上补丁后，这条规则不再命中同一个位置**。

它**不**证明代码逻辑上安全。绕过规则的写法同样能让它变绿。所以：

- 补丁仍然需要人 review（报告里给的是 diff，不是已落盘的文件）
- `--apply` 落盘前一定先看 diff
- 别把 `succeeded` 当成「安全」的同义词

## 运行 `fix` 的前提

`bee fix` 会在临时副本上跑补丁、编译、以及（开启 `--run-tests` 时）目标仓库的测试。
**测试是会执行代码的**，这等于执行任意代码。

- 只对可信仓库使用 `fix`
- 对第三方仓库先用 `scan` / `audit`（纯静态）
- 需要更强隔离就放进容器：见 `Dockerfile`
- `--rules-file` 同样会执行该 Python 文件

## 一句话版本

> 检测层够用就好，修复层必须有验证。
> 如果你是来找「更全的漏洞扫描器」，去用 Semgrep；如果是来找「修完能证明修对了」，
> 这才是 bee 的位置。
